## 1. 简历怎么写（四要素：场景→决策→难点→结果）

**项目名**：政策罗盘 PolicyCompass —— 跨城市社保/公积金政策 Agentic RAG 问答系统（个人项目）

**推荐 bullet（3~4 条，每条都有"决策+数字"）**：

- 面向社保/公积金政策咨询场景（同名政策各地标准不同、政策修订频繁、数字答错即事故），基于 LangGraph 设计 CRAG 自纠错检索编排：意图路由（城市/领域）→ 混合检索 → 相关性评分 → 黑话改写重检索（≤2 轮防死循环）→ Function Calling 额度计算 → 忠实度校验，校验两次不过自动降级为**诚实拒答**，库外问题拒答准确率 100%（评测集 4/4）；真实模型端到端 93.9%（33 题 smoke，计算/拒答/对比/黑话全对）与 93.3%（90 题 full，calc 15/15、refuse 12/12 零编造，holdout 单列 93.3%，冻结金标口径；金标修正后受影响条目子集重跑 100%）；语料 16 份真实政策文件（7 城+全国，每份注明 source_url，工具限额表对齐真实数字），另 7 份教学演示文档明确标注
- **手写 BM25（Okapi）+ 向量双路检索与 RRF 融合**，叠加城市/领域/政策标题三级业务加权与废止文件降权：自建 v1 33 题 smoke 回归集 + v2 90 题分层评测集（含 15 条 holdout 不参与调参）消融验证，recall@5 达 93~96%、MRR 0.83~0.90、**已废止政策泄漏 2→0**；接入 bge-reranker 重排并实现失败自动降级
- 定位并修复中文检索**分词粒度失配**问题（"杭州市住房公积金" vs "杭州公积金" 致 BM25 零命中），采用词 + CJK 字符 bigram 双通道索引（Lucene CJK 思路），术语类查询 recall 显著回升（可填你实测的前后数字）
- 工程化：FastAPI SSE token 级流式 + 全链路 trace（agent 决策路径实时推送/JSONL 留档）；LLM 调用指数退避重试、结构化输出**解析失败自校验纠错**（首错率与修复率可经 /api/stats 观测）；SQLite 增量索引（文件 hash 热更新）；Docker 一键部署；23 项 pytest 全绿（零 API key 的 mock 模式可跑 CI）；故障注入 5 场景 61 次**编造=0**（顺带修掉库外城市"张冠李戴"缺陷）、mock 压测 20/50/100 并发错误率 0

**一句话版**（投递系统的项目简介栏）：
> 把"政策问答"做成一个可靠系统：混合检索+业务加权、CRAG 自纠错、计算交给代码不交给模型、答不出就拒答——全部决策有评测数字背书。

**不要写的**（面试官一眼识别 demo）：
- ❌ "使用 LangChain 搭建 RAG + 调用 API 实现问答 + 使用向量库"
- ❌ 没有数字的"优化了检索效果"
- ❌ 把技术栈罗列当项目描述

## 2. 五分钟讲述脚本（面试自荐/项目介绍环节）

1. **场景与矛盾**（30s）：政策咨询是 RAG 最该做对的场景——答案有唯一正确性。但通用 RAG 在这里全错：北京上海同名政策额度不同（检索必须带城市）、政策会废止（旧文件会污染答案）、用户说"断缴"条文写"中断缴费"（词面失配）、贷款额度要算（LLM 心算不可靠）。
2. **架构与决策**（90s）：LangGraph 上做 CRAG——检索后先评分，不相关就用黑话词典改写重检索；涉及计算走 Function Calling，LLM 只抽参数、公式硬编码；生成后逐句忠实度校验，两次不过强制拒答。检索层手写 BM25 和 RRF 融合，叠加城市/标题/时效三类业务加权。
3. **两个踩坑故事**（90s）：
   - 分词粒度失配：评测时 BM25 召回为零，排查发现"杭州市住房公积金"和"杭州公积金"在 jieba 下词面完全不重叠，用词+字符 bigram 双通道解决；
   - 废止文件泄漏：消融发现纯 BM25 recall 最高但会把 2022 废止版带进上下文，加时效降权后泄漏归零，代价仅 1.9pp recall——政策场景这个交换必须做。
4. **结果与边界**（30s）：v1 33 题 smoke 回归集 + v2 90 题分层集（15 条 holdout 单列）+ 消融 + 故障注入 + 压测，证据链见 EVIDENCE.md；计算题 6/6 全对；诚实说明 mock 与真实模式的边界，测试替身只验证链路正确性。

## 3. 面试深挖预演（题题有本项目素材）

**Q1 哪些环节用 LLM 推理，哪些刻意硬编码？为什么？**
LLM：意图路由、文档相关性评分、黑话改写、参数抽取、生成、忠实度校验——全是语义模糊环节。硬编码：额度公式与限额表（可复算）、路由降级规则、循环上限、加权系数、拒答文案。原则：数字和流程必须确定性，语义理解交给模型；且 LLM 每个用法都有规则兜底（路由失败→规则路由、评分失败→保守分 0.3）。

**Q2 100 万人用，最先崩在哪？**
三层答案：① SQLite+内存索引是单机单写——但检索是纯内存只读，可多副本；真瓶颈是 LLM 串行调用（评分 N 次）；改进：粗排后只评 top3、批量评分接口、缓存高频问题（政策查询重复率高，缓存收益极大）。② 成本：评分+校验让每次问答 ~6-8 次 LLM 调用，用小模型跑评分/校验、大模型只做生成。③ 延迟：P50 目前 mock 30ms / 真实取决于 API；SSE 流式把首 token 时间和总时长解耦。

**Q3 工具调用失败/输出不合法的兜底？**
chat_json 解析失败→错误信息回灌重试 2 轮→仍失败抛结构化异常→上层降级（路由降规则、评分记 0.3、工具跳过继续生成）→全局兜底返回 SSE error 帧。全部计数在 /api/stats（json_first_pass_failure_rate）。

**Q4 评测集怎么建的？**
v1 33 题 smoke 回归集 + v2 90 题分层集（事实/对比/计算/拒答/时效/黑话/多跳七层，15 条 holdout 不参与调参），每题带期望文档、期望关键词、期望工具与额度数字——**金标全部对照语料原文与工具公式双验证，禁止凭记忆写数字**。检索指标（recall@5/MRR）用规则路由隔离 LLM 变量；端到端按题型分别判分（拒答看 refusal、计算看工具结果数字、其余看关键词与引用）。消融验证加权信号贡献。

**Q5 检索与模型知识冲突？**
政策场景的解法是结构性防御：答案只允许来自检索上下文（生成 prompt 硬约束 + 忠实度逐句校验 + 引用文号）；检索不到→拒答。模型自身知识永远不作为答案来源。

**Q6 为什么 LangGraph？Dify 行不行？**
需要显式状态机：条件边（评分阈值）、有界循环（改写≤2）、retry 语义——LangGraph 的 StateGraph 是最小足够抽象。Dify 适合流程固定的低代码场景，但条件循环、自定义评分器、token 级流式接管这类精细控制力不够；AutoGen/CrewAI 面向多 agent 对话协作，本项目是单 agent 多阶段流水线，不需要。

**Q7 对话变长/成本控制？**
history_window 截断（默认 6 轮）+ checkpointer 按线程隔离；评分只对 top5；生成的上下文按 chunk 压缩。改进方向：分层记忆（长期存用户画像如"杭州缴存/已婚"，检索时作为路由先验）。

**Q8 RAG 热更新？**
文件 hash 增量：未变跳过、变了删旧 chunk 重切重嵌、删除级联清理；政策修订场景额外用 status 元数据——旧版保留可检索（可回答"新旧差异"）但强降权不进正常答案。实测 23 份文档（10 真实×7城 + 13 演示）二次同步秒级完成（hash 未变全跳过）。

**Q9 项目最大的坑？**
两个候选：① 分词粒度失配（见讲述脚本）——教训是"检索质量问题的第一嫌疑人是文本处理而不是算法"；② mock 测试替身与真实 prompt 的契约漂移——chat_json 会注入 schema 消息导致 mock 读错 task 标记，修复后确立"测试替身必须走真实调用路径"的原则（mock 继承真实 client 只覆写网络层）。

**Q10 还会怎么演进？**
对比题子问题并行检索；缓存层；评分用小模型；Langfuse 生产观测；给 Datawhale All-in-RAG 投 Agentic RAG 章节（教程明确欢迎该专题投稿，本项目就是现成素材）。
