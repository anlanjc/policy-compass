## 1. 双通道分词：一次真实的零召回事故（bm25.py:48-61）

```python
def tokenize(text: str) -> list[str]:
    """词 + CJK 字符 bigram 双通道分词（Lucene CJK 分析器思路）。"""
    words = tokenize_words(text)
    bigrams: list[str] = []
    for w in words:
        if any(_is_cjk(c) for c in w):
            bigrams.extend(w[i : i + 2] for i in range(len(w) - 1))
    return words + bigrams
```

**因果链**（bm25.py docstring 50-55 的原话展开，PROJECT_BOOK 踩坑实录第 1 条）：

1. jieba 对文档 `"杭州市住房公积金租赁提取"` 切出**整词**`["杭州市", "住房公积金", "租赁", "提取"]`；
2. 用户查询 `"杭州公积金"` 被 jieba 切成 `["杭州", "公积金"]`——**粒度不一致**；
3. BM25 按 token 精确匹配计 tf：查询的 `"杭州"`、`"公积金"` 在文档 token 列表里**一个都对不上**；
4. 所有文档得分为 0 → **零召回**，且没有任何报错，检索层"静默失败"。

**修复思路**：对每个含 CJK 的词，追加其字符 bigram（`"杭州市" → ["杭州","州市"]`），查询与文档**同法处理**。这样查询 bigram `"杭州"` 与文档 bigram `"杭州"` 必然对齐，失配消除。关键取舍：bigram 作为**普通 token** 参与 tf/idf，不加特殊权重——因为 IDF 已经天然给"在文档集中罕见的 bigram"更高权重，再人为加权反而破坏概率模型。

两个辅助函数：
- `tokenize_words`（bm25.py:27-35）：jieba 词级，过滤 `len>=2 或纯数字` 的 token——单字词太泛；
- `cjk_bigrams`（bm25.py:38-45）：**纯 CJK 字符**的相邻 bigram 集合（标点天然被剥离），用于标题重叠计算（见 §4），测试 `tests/test_retrieval.py:13-16` 验证 `《杭州市，办法》` 产出 `杭州/办法/市办`。

双通道的测试锚点（tests/test_retrieval.py:6-10）：`tokenize("杭州公积金")` 和 `tokenize("杭州市住房公积金租赁提取")` 必须共享 bigram `"杭州"`。

## 2. 手写 BM25：公式逐项对应代码（bm25.py:70-114）

公式（模块 docstring，bm25.py:7-8）：

```
score(q,d) = Σ IDF(qi) · f(qi,d)·(k1+1) / (f(qi,d) + k1·(1-b+b·|d|/avgdl))
IDF(qi)    = ln(1 + (N - n(qi) + 0.5) / (n(qi) + 0.5))
```

| 符号 | 代码位置 | 含义与"管什么" |
|---|---|---|
| k1=1.5 | config.py:67，bm25.py:72 | 词频饱和度：f 越大加分越少（(k1+1) 与分母的 f 对冲） |
| b=0.75 | config.py:68，bm25.py:73 | 文档长度归一强度：长文档不该天然占优 |
| IDF 加 1 | bm25.py:88-90 | `ln(1 + ...)` 保证**非负**——测试锚点 `idx.idf("公积金") > 0`（tests/test_retrieval.py:28） |

`__init__`（bm25.py:71-86）预计算每文档 token 列表、tf Counter、doc_len 与 df（文档频率）、avgdl。

`search`（bm25.py:92-94）是 `search_weighted({t: 1.0}, top_k)` 的语法糖。`search_weighted`（bm25.py:96-114）三处细节：

1. `if term not in self.df: continue`（bm25.py:102-103）——查询里库中不存在的词直接跳过（idf 无意义）；
2. 打分累加 `weight * idf * f * (k1+1) / denom`（bm25.py:112）——**权重乘在整项上**，这就是黑话扩展词低权重注入的入口；
3. `denom = f + k1·(1 - b + b·|d|/avgdl)`，`avgdl` 为 0 时用 `or 1` 防除零（bm25.py:109-111）。

**词权的用途**：黑话扩展。`HybridRetriever.expand_query`（hybrid.py:80-90）：查询命中黑话词典（`data/lexicon.json`，`_load_lexicon` hybrid.py:67-72）后，规范词以 **0.6** 权重注入、原始词保持 **1.0**——"扩展词不能淹没原始查询意图"。测试锚点 tests/test_retrieval.py:31-37（混合权重下原始词仍是主信号）与端到端锚点 r3（"跳槽了公积金怎么带走"→ expanded_terms 含"转移接续"，tests/test_retrieval.py:114-115）。

为什么手写而不用 rank_bm25/LangChain？模块 docstring（bm25.py:3-5）：BM25 是面试高频考点，逐行实现才能讲清 idf 饱和、长度归一各解决什么；同时 `search_weighted` 的词权入口是扩展词低权重注入的前提——现成库不一定暴露这个口子。

## 3. RRF 融合与双路并行（hybrid.py:94-188)

### 3.1 并行设计（hybrid.py:111-116）

```python
bm25_task = asyncio.get_running_loop().run_in_executor(
    None, lambda: self._bm25.search_weighted(weighted, settings.top_k_recall) ...
)
vec_task = asyncio.ensure_future(self._vector_search(query, settings.top_k_recall))
bm25_hits, vec_hits = await asyncio.gather(bm25_task, vec_task)
```

BM25 是 CPU 密集（纯 Python 循环打分）→ `run_in_executor` 丢线程池；向量检索是网络 IO（embedding API）→ `ensure_future` 协程。`gather` 汇合——**检索延迟 ≈ max(两路) 而非求和**（hybrid.py:9-10）。两路各召回 `top_k_recall=20`（config.py:61）。

`_vector_search`（hybrid.py:145-161）是手写余弦：`matrix @ (q/norm)`，`sims[i] > 0` 过滤（hybrid.py:161）。

### 3.2 RRF（hybrid.py:165-188）

```python
k = settings.rrf_k            # config.py:63 → 60
for rank, hit in enumerate(bm25_hits, start=1):
    sc.fused_score += 1.0 / (k + rank)                     # bm25 路满权
for rank, (idx, _) in enumerate(vec_hits, start=1):
    sc.fused_score += settings.vector_weight / (k + rank)  # 向量路 ×0.8
```

两个要点：
- **只看排名不看原始分**：BM25 分与余弦相似度量纲完全不同，RRF 用 `1/(k+rank)` 把两路都映射到同一把"排名尺"上。k=60 的作用是**排名平滑**——第 1 名（1/61）与第 2 名（1/62）差距只有约 1.6%，头部排名的微小扰动不会剧烈改变融合结果。
- **向量路权重 0.8**（config.py:64-66，带注释）：实测 embedding 质量不稳定时向量路噪声会污染融合排序，降权护住 BM25 主信号；真实 bge-m3 下可回调 1.0。

`candidates = fused[: max(top_k * 3, 12)]`（hybrid.py:119）——取融合前 12~15 个进 rerank，`top_k_final=5`（config.py:62）是最终进入生成的数量。

### 3.3 rerank 可降级（hybrid.py:121-140）

有 rerank key 时用 bge-reranker 交叉编码器重排（rerank.py:27-42），`final_score` 换成交叉编码器分；**任何异常捕获后降级为 RRF 融合序**，`stats.incr("rerank_fallbacks")` 记数（hybrid.py:135-138）——"检索链路任何一环失效都不应导致整体不可用"（rerank.py:4）。

## 4. 业务元数据加权：五条乘法规则（hybrid.py:190-208）

RRF 之后、rerank 之前（或无 rerank 时即终序），对融合分做一串乘法。每一级对应一条业务约束（hybrid.py:3-7 docstring + config.py:69-72）：

| 规则 | 系数 | 代码 | 防什么 |
|---|---|---|---|
| 城市命中加权 | ×1.8（city_match_boost） | hybrid.py:197-198 | 同名政策各地标准不同：查"杭州租房提取"召回上海文件 |
| 其他城市强降权 | ×0.5 | hybrid.py:199-200 | 已明确指向某城市时，外地文件不该挤进前排 |
| 领域命中加权 | ×1.3（domain_match_boost） | hybrid.py:201-202 | 公积金/社保混检串台 |
| 标题重叠加权 | ×1.6（title_match_boost） | hybrid.py:203-206 | 政策标题=事项名，是比正文更强的主题信号：查询与标题的 `cjk_bigrams` 重叠 **≥4 个且 ≥25%** 才乘 |
| 已废止降权 | ×0.3（invalid_doc_penalty） | hybrid.py:207-208 | 旧版文件保留可检索（能答"政策变了什么"），但正常问答不排在现行文件前 |

**为什么加权放在 RRF 之后**（PROJECT_BOOK 技术选型表 + CODE_GUIDE 考点）：RRF 已经把两路归到统一量纲，在其融合序上加权，避免原始分数量纲互相干扰；如果加权做在 BM25 内部，向量路完全感知不到城市/领域信号。

**废止降权的完整故事**（PROJECT_BOOK 踩坑实录第 2 条）：纯 BM25 时 recall 最高，但旧版文件与新文件同分进 Top5 → 用户拿到已废止的 1500 元/月标准 → 加 ×0.3 后泄漏 2→0。注意降权而非过滤——`is_valid=False` 的文件仍在索引里，时效类问题反而**需要**旧文件。

端到端锚点：tests/test_retrieval.py:95-111——北京城市限定召回 `beijing_rent_extract.md`；杭州真实语料召回 `hz_rent_limit_2023.pdf`（文号"杭房公委〔2023〕8号"、is_valid=True）。

## 5. 常见错误实现对比

| 错误写法 | 后果 | 正确做法（源码位置） |
|---|---|---|
| 只用 jieba 词级分词 | 粒度失配零召回且静默失败 | 词+bigram 双通道（bm25.py:48-61） |
| bigram 加特殊高权重 | 破坏 tf/idf 概率语义，短 bigram 噪声放大 | bigram 作普通 token（bm25.py:56-61） |
| RRF 改成"分数归一化加权和" | BM25 分与余弦量纲不可比，调参地狱 | 只用排名 1/(k+rank)（hybrid.py:181-188） |
| 城市不匹配直接过滤 | 多城对比、全国性文件被误杀 | ×0.5 软降权，"全国"文件豁免（hybrid.py:197-200） |
| 废止文件从索引删除 | "政策变了什么"类问题无法回答 | ×0.3 降权保留（hybrid.py:207-208） |
| 扩展词与原词同权 | 黑话词噪声淹没用户原意 | 0.6 vs 1.0（hybrid.py:86-89） |
| BM25 同步阻塞事件循环 | 向量路等 BM25 算完才开始网络请求，延迟相加 | run_in_executor + gather 并行（hybrid.py:111-116） |

## 6. 面试讲法

**30 秒版**：
> 检索是 BM25 加向量双路并行，RRF 融合，再做业务元数据加权。BM25 是手写的，分词用词+bigram 双通道——因为 jieba 对文档切"杭州市住房公积金"整词、查询切"杭州公积金"，粒度失配导致 BM25 零命中且静默失败，bigram 让查询和文档在字符层面必然对齐。RRF 的 k=60 做排名平滑，两路只用排名不用原始分，避开量纲问题。加权五条规则对应业务约束：命中城市 ×1.8、外地 ×0.5、领域 ×1.3、标题事项名重叠 ×1.6、已废止 ×0.3——降权不是过滤，时效类问题还要靠旧文件。

**3 分钟版**：
- 第一分钟：讲零命中事故的完整因果链（切分不一致 → tf 全零 → 静默失败），修复的取舍（bigram 不加特殊权重的理由）。
- 第二分钟：BM25 公式默写 + k1/b 各管什么 + IDF 加 1 为什么非负；`search_weighted` 词权入口如何支撑黑话 0.6 权重注入。
- 第三分钟：并行设计（CPU 路线程池、IO 路协程，延迟取 max）→ RRF → 五级加权逐条给业务理由，引用废止泄漏 2→0 的消融数字收尾。

## 7. 自测五题（答案见文末折叠区）

1. `"杭州公积金"` 在双通道下产出哪些 token？哪些来自词通道、哪些来自 bigram 通道？
2. RRF 里为什么 BM25 路权重是 1.0 而向量路是 0.8？什么时候应回调？
3. 城市加权为什么对 `city == "全国"` 的文档豁免？如果不豁免会怎样？
4. 标题加权的触发条件为什么是"重叠 ≥4 个且 ≥25%"两个条件同时满足？
5. `idf` 公式里 `+1`（`ln(1 + ...)`) 如果去掉会出什么问题？

<details>
<summary><strong>答案（先自己答再看）</strong></summary>

1. 词通道：`["杭州", "公积金"]`（均 len≥2 保留）；bigram 通道：对每个含 CJK 的词追加相邻字符对——`"杭州"→["杭州"]`、`"公积金"→["公积","积金"]`。合并后 `["杭州","公积金","杭州","公积","积金"]`（词+bigram 拼接，bm25.py:56-61）。
2. 实测 embedding 质量不稳定时向量路噪声会污染融合排序（config.py:64-66 注释），0.8 护住 BM25 主信号；当换用高质量 embedding（如真实 bge-m3）且验证向量路精度后可回调 1.0。
3. "全国"文件对所有城市都适用——它是"最大公 denominator"，不该因用户问了某个具体城市而被 ×0.5。若不豁免，"杭州租房提取"的全国性规定会排到杭州本地文件后面，甚至挤出 top_k，答案丢失普适条款。
4. 单看数量：长查询与长标题天然重叠多，短查询可能只差 1 个 gram 就错过；单看比例：短标题（如 4 个 bigram）一击即中 25% 但可能只是泛词。两条同时满足才说明"主题词面真重叠"——这是防误伤的保守双门槛（hybrid.py:205）。
5. `n(qi)=0`（词未出现）时 `(N+0.5)/0.5` 很大，`ln(N+1.5)` 仍为正——去掉 +1 后括号可能 <1（极端小语料），ln 出负值，未命中词反而贡献负分；加 1 保证 idf ≥ 0，与测试锚点 `idx.idf("公积金") > 0` 一致（bm25.py:88-90）。
</details>
